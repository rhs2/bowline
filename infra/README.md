# Bowline infrastructure

Everything AWS-facing lives here. Nine Terraform modules describe one Bowline
environment; three root configurations compose them into `staging`, `prod` and a
`shared` account-level root that holds the container registries and the identity
the deploy workflow assumes.

Nothing in this directory contains a real account id, ARN, hostname or secret.
Every placeholder uses `000000000000` for the account and `bowline.example` for
the domain. Credentials are generated by Terraform into AWS Secrets Manager and
are never written to state files in plain text beyond what Terraform inherently
stores, which is why the state bucket is encrypted and private.

## Layout

```
infra/
  README.md                     this file
  .gitignore                    tfvars, plans and crash logs
  terraform/
    modules/
      network/                  VPC, three subnet tiers, NAT, endpoints, security groups, flow logs
      database/                 RDS PostgreSQL 16, parameter group, four credential secrets
      cache/                    ElastiCache Redis 7 replication group, AUTH token secret
      storage/                  Two private S3 buckets, KMS key, CORS, TLS-only bucket policy
      secrets/                  JWT signing key, internal service token, JSON bundle
      mail/                     SES domain identity, DKIM, configuration set, SMTP credential
      ecr/                      One repository per service, scan on push, lifecycle policy
      ecs/                      Fargate cluster, ALB, Cloud Map, IAM, task definitions, services, autoscaling
      observability/            Log groups, SNS topic, eleven alarms, outbox depth metric filter
    environments/
      shared/                   ECR repositories and the GitHub OIDC deploy role (one per account)
      staging/                  Small, single-AZ, quick to destroy
      prod/                     Three AZs, Multi-AZ database, deletion protection
```

Every module carries `main.tf`, `variables.tf` (typed, every variable
documented), `outputs.tf`, `versions.tf` and a `README.md` describing what it
creates and why. Every root and every module pins `required_version >= 1.9` and
the AWS provider at `~> 5.70`.

### Module dependency order

The roots wire the modules together in this shape. Arrows point from producer to
consumer.

```
network ──┬─> database ──┐
          ├─> cache ─────┤
          └─> ecs <───────┴── secrets, storage, mail
                │  ^
                │  └── observability (log group names)
                └───> observability (ALB, target group, cluster and service names for alarms)
```

`ecs` and `observability` reference each other, which is legal because the
dependency runs through different resources in each direction: the log groups do
not depend on anything in `ecs`, and the alarms are the only things that depend
on `ecs` outputs. Terraform resolves this as a straight line, not a cycle.

## Validating a change

Terraform does not need to be installed locally. Both commands below are exactly
what the `terraform` job in `.github/workflows/ci.yml` runs, so a clean result
here means a green job there.

```
cd infra/terraform
docker run --rm -v "$PWD":/w -w /w hashicorp/terraform:1.9.8 fmt -check -recursive

for d in modules/* environments/*; do
  echo "== $d"
  docker run --rm -v "$PWD":/w -w "/w/$d" hashicorp/terraform:1.9.8 init -backend=false -input=false >/dev/null
  docker run --rm -v "$PWD":/w -w "/w/$d" hashicorp/terraform:1.9.8 validate
done
```

`fmt -check -recursive` must print nothing. `validate` must print
`Success! The configuration is valid.` for all twelve directories.

## Bootstrapping the state backend

Every root stores state in one S3 bucket and takes its lock from one DynamoDB
table. Terraform cannot create its own backend, so these two resources are made
once, by hand, with the AWS CLI, by an operator with administrative access.

Pick names first. The bucket name must be globally unique, so it carries the
account id; the defaults baked into `backend.tf` and into the `shared` root's
`state_bucket_name` and `state_lock_table_name` variables are
`bowline-terraform-state-<account id>` and `bowline-terraform-locks`.

```
export AWS_REGION=us-east-1
export ACCOUNT_ID=000000000000
export STATE_BUCKET="bowline-terraform-state-${ACCOUNT_ID}"
export LOCK_TABLE="bowline-terraform-locks"

# 1. The bucket. us-east-1 rejects a LocationConstraint, other regions require it.
aws s3api create-bucket --bucket "$STATE_BUCKET" --region "$AWS_REGION"

# 2. Versioning, so a corrupted or truncated state file can be rolled back.
aws s3api put-bucket-versioning --bucket "$STATE_BUCKET" \
  --versioning-configuration Status=Enabled

# 3. Encryption at rest.
aws s3api put-bucket-encryption --bucket "$STATE_BUCKET" \
  --server-side-encryption-configuration \
  '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"AES256"},"BucketKeyEnabled":true}]}'

# 4. No public access, ever. State files contain resource identifiers and,
#    for some resources, generated values.
aws s3api put-public-access-block --bucket "$STATE_BUCKET" \
  --public-access-block-configuration \
  'BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true'

# 5. The lock table. LockID is the only attribute Terraform needs.
aws dynamodb create-table --table-name "$LOCK_TABLE" \
  --attribute-definitions AttributeName=LockID,AttributeType=S \
  --key-schema AttributeName=LockID,KeyType=HASH \
  --billing-mode PAY_PER_REQUEST --region "$AWS_REGION"
```

If the names differ from the defaults, either edit the three `backend.tf` files
and the two `shared` variables, or leave the files alone and pass the values at
init time:

```
terraform init \
  -backend-config="bucket=my-state-bucket" \
  -backend-config="dynamodb_table=my-lock-table"
```

State keys are `shared/terraform.tfstate`, `staging/terraform.tfstate` and
`prod/terraform.tfstate` in the one bucket.

## The deploy role and GitHub OIDC

`deploy.yml` never uses a long-lived access key. It requests an OIDC token from
GitHub (`permissions: id-token: write`) and exchanges it for temporary AWS
credentials by assuming a role. The `shared` root creates both halves: the OIDC
provider for `token.actions.githubusercontent.com` and the role itself,
`bowline-github-deploy` by default.

Apply `environments/shared` first and read the ARN off the output:

```
cd infra/terraform/environments/shared
terraform init
terraform apply
terraform output -raw deploy_role_arn
```

Store that ARN as the repository secret `AWS_DEPLOY_ROLE_ARN`. That is the only
AWS secret GitHub needs.

### The trust policy

The `shared` root builds this policy from `github_repository`, `deploy_branches`
and `deploy_environments`. Written out with the defaults, it looks like this.
Nothing else in the world can assume the role.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "GitHubActions",
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::000000000000:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
        },
        "StringLike": {
          "token.actions.githubusercontent.com:sub": [
            "repo:rhs2/bowline:ref:refs/heads/main",
            "repo:rhs2/bowline:environment:staging",
            "repo:rhs2/bowline:environment:prod"
          ]
        }
      }
    }
  ]
}
```

Three subjects, because `deploy.yml` has three kinds of job:

| Job         | Runs as                              | Matching subject                          |
|-------------|--------------------------------------|-------------------------------------------|
| `images`    | a plain push to `main`               | `repo:rhs2/bowline:ref:refs/heads/main`   |
| `terraform` | inside the `staging` or `prod` GitHub environment | `repo:rhs2/bowline:environment:<env>` |
| `migrate`   | the same environment                 | `repo:rhs2/bowline:environment:<env>`     |

The `aud` condition is what stops a token minted for a different audience from
being replayed here. The `sub` condition is what stops a fork, another branch or
another repository from assuming the role. Both conditions are required; a trust
policy with only the `Federated` principal and no `sub` condition would let any
GitHub Actions workflow anywhere assume it.

The `environment:` subjects also mean the protected-environment approval in
GitHub is a real gate rather than a convention: without the environment, the job
never gets a token whose subject matches, so it cannot reach AWS at all.

### What the role may do

`deploy` grants full control over a list of service prefixes
(`deploy_role_services`: ecs, ecr, rds, elasticache, ec2, elasticloadbalancing,
s3, secretsmanager, ssm, logs, cloudwatch, sns, kms, route53, acm,
servicediscovery, application-autoscaling, dynamodb), plus:

- `iam:*` restricted to `bowline-*` roles and policies, so the deploy role can
  create and pass task roles but cannot touch anything else in IAM;
- read-only IAM and `iam:CreateServiceLinkedRole` account-wide, which ECS,
  ElastiCache and autoscaling need on first use;
- read and write on the state bucket and the lock table only.

If the OIDC provider already exists in the account (an account may hold only one
for GitHub), set `create_oidc_provider = false` and pass `oidc_provider_arn`.

## Order of a first deploy

Run these once, in this order. Steps 1 and 2 are manual and happen once per
account; from step 4 onwards the workflow does the same thing on every push.

1. **State backend.** The bucket and lock table, as above. Nothing else works
   without them.

2. **Registries and identity.** Apply `environments/shared`. This creates the
   five ECR repositories (`bowline/api`, `bowline/web`, `bowline/billing`,
   `bowline/analytics`, `bowline/notify`) and the deploy role. Copy
   `deploy_role_arn` into the `AWS_DEPLOY_ROLE_ARN` repository secret and create
   the `staging` and `prod` GitHub environments with the reviewers who should
   approve a production apply.

3. **Certificates and DNS.** Request an ACM certificate in the deploy region
   covering `app.bowline.example` (and `staging.bowline.example`), validate it,
   and note the ARN. If Route 53 hosts the zone, note the zone id: passing
   `route53_zone_id` lets Terraform create the application alias record and the
   SES DKIM, MAIL FROM and DMARC records itself. Put both values in the
   environment's `terraform.tfvars`.

4. **Images.** Push one image per service to ECR, tagged with the twelve
   character commit SHA. The `images` job in `deploy.yml` does this; the first
   time round it can be done by hand after `aws ecr get-login-password`. The
   infrastructure step needs the tag to exist, because ECS will try to pull it.

5. **Infrastructure.** Apply the environment root with that tag:

   ```
   cd infra/terraform/environments/staging
   terraform init
   terraform apply -var image_tag=<sha>
   ```

   Roughly 176 resources in staging and 187 in production. The first apply takes
   about twenty five minutes, most of it RDS and ElastiCache. The `api` and `web`
   services will not reach a steady state yet, because the database has no
   schema and no application roles, so their health checks fail. That is
   expected and the next step fixes it.

6. **Migrate.** Run the one-off task. It connects as the RDS master user, creates
   the `bowline_app`, `bowline_ro` and `bowline_notify` roles with the passwords
   Terraform generated, then applies every migration in `db/migrations`. This is
   the only thing that ever uses the master credential.

   ```
   aws ecs run-task --cluster bowline-staging \
     --task-definition bowline-migrate-staging --launch-type FARGATE \
     --network-configuration "$(aws ssm get-parameter \
        --name /bowline/staging/migrate-network \
        --query Parameter.Value --output text)"
   ```

   Wait for the task to stop and confirm `exitCode` is 0. The deploy workflow
   does exactly this (`aws ecs wait tasks-stopped`, then read
   `containers[0].exitCode`) and fails the job on a non-zero code, so a failed
   migration cannot report as a successful deploy. Within a minute or two the
   services pass their health checks and the ALB starts serving.

7. **Seed (staging only).** The 260-person demo company comes from the `seed`
   binary in the same image. Run it the same way as the migrate task with the
   command overridden, or run it locally against the staging database through a
   bastion. Never seed production: it creates users with a known password.

8. **Verify.** Open `https://staging.bowline.example`, log in, and confirm
   `/healthz` and `/readyz` both answer. `docs/RUNBOOK.md` covers everything
   after this point.

Production repeats steps 3 to 6 with `environments/prod` and the `prod` GitHub
environment.

### Why the migrate family carries the environment

The migration task definition is `bowline-migrate-<env>`, not a single shared
`bowline-migrate`, and that is worth understanding rather than copying.

ECS task definition families are **account-wide**, and `run-task` given a family
with no revision number resolves to the newest revision of that family. A shared
family would therefore receive revisions from both environments, and whichever
was applied most recently would win. That is not a naming inconvenience: each
revision embeds the secret ARNs of the environment that created it, including
the RDS master credential. A staging deploy resolving to a production revision
would run migrations against the production database with the production master
credential, from a job nobody was watching closely because it was only staging.

Putting the environment in the family name removes the ambiguity structurally.
`deploy.yml` resolves `FAMILY="bowline-migrate-$ENVIRONMENT"` and the `ecs`
module derives the same name from its `environment` variable, so the two cannot
drift and the safety does not depend on the environments being in separate
accounts, nor on the workflow happening to apply and migrate back to back.

Separate accounts per environment are still the better posture for other reasons
(blast radius, quota isolation, billing), and the `shared` root's
`pull_account_ids` variable supports it by letting a production account pull
images from the account that builds them. It is simply no longer load-bearing for
this particular hazard.

The workflow also waits for the task and checks its result: `aws ecs wait
tasks-stopped`, then `containers[0].exitCode`, failing the job when it is
non-zero. A migration that fails now fails the deploy instead of passing
silently.

To override the derived name, set `migrate_task_family` on the `ecs` module, and
change `deploy.yml` to match.

## Cost notes

Rough monthly figures at us-east-1 on-demand list prices, for the resources
Terraform creates and nothing else. Data transfer, request charges and support
are excluded, and prices change, so treat these as the shape of the bill rather
than a quote.

### Staging: roughly 170 to 200 USD per month

| Item                                            | Approximate |
|-------------------------------------------------|-------------|
| Fargate, 1.5 vCPU and 3 GiB across five services | 55          |
| RDS `db.t4g.medium`, single-AZ, 20 GiB gp3       | 50          |
| One NAT gateway                                  | 33          |
| Application load balancer                        | 18          |
| ElastiCache, one `cache.t4g.micro`               | 12          |
| Secrets Manager, seven secrets                   | 3           |
| CloudWatch logs (14 day retention) and alarms    | 5 to 15     |

### Production: roughly 800 to 1000 USD per month

| Item                                                        | Approximate |
|-------------------------------------------------------------|-------------|
| RDS `db.m7g.large`, Multi-AZ, 100 GiB gp3, 35 day backups    | 320         |
| Fargate, 5.25 vCPU and 10.5 GiB at the minimum desired count | 190         |
| Three NAT gateways, one per AZ                               | 99          |
| Four interface VPC endpoints across three AZs                | 88          |
| ElastiCache, two `cache.t4g.small` with failover             | 47          |
| CloudWatch logs (90 days), Container Insights, alarms        | 40 to 90    |
| Application load balancer                                    | 20          |
| Secrets Manager, S3, KMS, SES                                | 10          |

Autoscaling can add up to four more `api` tasks and two more `web` tasks, which
is another 150 or so at full stretch.

### The levers that actually matter

- **NAT gateways.** Three of them cost more than the load balancer and the cache
  combined, and they also charge per gigabyte processed. `single_nat_gateway =
  true` cuts this to a third at the price of an AZ-level single point of failure.
  Staging already does this; production deliberately does not.
- **Interface endpoints.** The four in production (ECR API, ECR Docker,
  CloudWatch Logs, Secrets Manager) cost about 88 a month but remove image pulls,
  log shipping and secret fetches from the NAT path, where they would be charged
  per gigabyte. Image pulls are the bulk of that traffic, so the endpoints
  roughly pay for themselves and keep the traffic off the public internet.
  Staging turns them off and accepts the NAT charge.
- **Multi-AZ RDS.** Doubles the instance cost. It is the largest single line in
  production and the reason staging is single-AZ.
- **Log retention.** Ninety days in production against fourteen in staging.
  Ingestion is the dominant charge, not storage, so lowering retention helps less
  than turning down `RUST_LOG`.
- **Container Insights.** Enabled on the cluster because the
  `running-below-desired` alarms are built on its metrics. It bills per metric
  per service and is the most variable line in the table.

Staging is safe to destroy overnight. `deletion_protection` is false, buckets
have `force_destroy = true`, the database skips its final snapshot and secrets
have a zero day recovery window, so `terraform destroy` completes without manual
cleanup. Production is the exact opposite by design, and a `destroy` there will
stop on the load balancer and the database until someone deliberately turns the
protections off.
